# 面试问题与参考答案（技术类）

> 围绕本项目的架构、实时音频、LLM 编排、工程实践类问题。
> 答案基于项目真实实现编写，面试时可按深度要求扩展或精简。

---

## 一、总体架构

### Q1：介绍一下项目的整体架构
**A**：分层架构，六层：
- **接入层（Channel）**：WebRTC 信令（offer/answer/ICE）+ 音频通道。注意：WebRTC 只用于建立连接，**音频不走 WebRTC 音轨**——浏览器以 16kHz PCM16 二进制帧经信令 WebSocket 直传后端（实测本机 opus 解码输出损坏，ASR 无法识别）。
- **语音引擎（Engine）**：Silero VAD 状态机、会话状态机（IDLE/LISTENING/THINKING/SPEAKING/CLOSED）、SpeechJoiner（LLM token 流 → TTS 帧流衔接）。
- **对话编排层（Orchestration）**：AgentScope 封装——纯文字进出；含共享状态多智能体编排与上下文管理（稳定前缀 + 滑窗）。
- **话术引擎（Flow）**：意图中枢状态机（开场白→意图识别→处理节点循环→结束语）、意图分类器、流程图定义与校验。
- **Provider 层**：ASR/LLM/TTS 三环节各自独立接口，本地（FunASR/CosyVoice2）与云端（火山/千问/DeepSeek）配置驱动切换。
- **业务与数据层**：FastAPI 路由 + SQLAlchemy 2.x + PostgreSQL 16（场景/人设/流程/工具/客户/通话记录）。
前端是 Vue 3 + TS + Tailwind v4 管理台（对话工作台、vue-flow 流程图编辑器、各管理页）。

### Q2：为什么音频用 PCM 直传而不是 WebRTC 音轨？
**A**：这是个实测驱动的决策。本机环境（联想立体声麦克风阵列 + Chrome）下，aiortc 的 opus 解码输出损坏（48k 假标签 + 逐样本重复，听感「慢放猪叫」），ASR 完全无法识别。改走 PCM 直传后问题消失。收益：链路简单可控、无编解码延迟、方便直连 ASR；代价：无丢包重传，但本产品是局域网/低延迟场景，可接受。**教训沉淀在项目文档里：标准不等于正确，实测数据优先。**

### Q3：三环节（ASR/LLM/TTS）如何做到可切换？
**A**：每环节一个 Provider 接口 + 工厂函数，配置 = `kind + base_url + api_key + model`。切换 = 改配置：Web 面板保存后调用 `invalidate_shared_providers()` 使进程级单例失效，下一路会话按新配置重建（本地模型显存随旧实例 GC 释放）——**热切换，零重启**。本地↔云端走同一抽象，业务层不感知差异。

## 二、实时语音与打断

### Q4：全双工打断是怎么实现的？
**A**：双路触发 + 五步动作链。
- **触发**：① VAD 起音（250ms 观察窗过滤杂音）；② ASR 驱动——机器人回复期间转写出字即判定抢话（比 VAD 起音更快）。
- **动作链**（顺序）：引擎清空未播队列并返回「已完整说出的句子」快照 → 取消回复任务（token 流 aclose → LLM 关流）→ 前端收到 stop_audio 立即停掉已调度的播放帧 → 打断计数 + 气泡标记。
- **上下文重建**：下一轮回复时，把已说句子以 assistant 身份注入历史（一句没说完则注入「上一句回复被打断」占位）——保证 user→assistant→user 的消息形态，防止模型把历史问题逐个补答。
- **打断窗口**：后端生成中 或 前端播报中（用「已发送帧序号 vs 已确认播放帧序号」判定）。

### Q5：讲一个打断相关的疑难 bug 和你的排查方法
**A**：「说完话不回复」的偶发卡死。表象随机，最后靠全链路日志抓到时序：客户打断开场白 → 客户说完 → VAD 端点事件发出 → 但此刻打断窗口未收敛（前端还没回 playback_done）→ 端点被挡丢弃。关键在：**VAD 端点是边缘触发（一段静音只发一次），丢弃后不会重发** → 收尾永远不启动。修复：端点被挡不丢弃，挂起 `pending_end` 标记，后台轮询等打断窗口收敛后补执行 flush；客户再开口则作废交新端点。方法论：偶发竞态不要猜，让日志把时序讲出来。

### Q6：VAD 和 ASR 的「收尾」怎么处理句尾延迟？
**A**：云端 ASR（千问）是句级修订语义：中间结果 text 为空（快照语义），最终句要等服务端判停后才推。收尾流程：VAD 端点 → `flush_asr()` 三段式（剩余真实音频 → 追喂 2 块静音释放句尾 → 静音块 final 收尾 → reset）→ 收尾宽限（settle 窗口等判停增量并入，最多 5s，期间新语音到达则作废交新轮）→ join 完整转写 → 提交回复。收尾任务单引用串行化，防止两个收尾并发 join 混句。

### Q7：如何做到低延迟（TTFT）？
**A**：五层优化：
1. **首 token 即触发 TTS**：SpeechJoiner 不等 LLM 整句，遇标点（。！？，等）或达阈值即切段合成；
2. **意图关键词快路径**：本地子串匹配 0ms，未命中才走 LLM 结构化分类（max_tokens≈20 + 稳定前缀命中上下文缓存，约 150~300ms）；
3. **稳定前缀 + Prompt 缓存**：system prompt（人设 + 合规边界）字节级稳定靠前，变化内容靠后——DeepSeek 上下文缓存持续命中；
4. **上下文管控**：历史滑窗按 token 预算裁剪；
5. **音频帧并发推送**：TTS 帧进引擎 FIFO，排空任务边到边推，不等整轮合成完。

### Q8：为什么 VAD 打断比纯靠 ASR 更可靠？
**A**：VAD 起音是能量级判定，对「还没说清但已经开口」的抢话也能触发（比如客户「嗯…」）；ASR 驱动更快但要求转写出字。两者互补：VAD 保证不漏、ASR 保证更快。另外打断窗口用「后端生成中 ∨ 前端播报中」双条件，避免「AI 播报尾声用户抢话被误判为正常轮次」。

## 三、LLM 编排（AgentScope）

### Q9：为什么用 AgentScope？它的边界是什么？
**A**：AgentScope 2.x 提供了智能体、工具调用（Toolkit + ReAct）、共享状态（AgentState）、结构化输出等能力。但项目约定它的边界是**纯文字进出**：只做「提示词 + 上下文 + 工具」的 LLM 编排，语音引擎、状态机、流程图全部自建。原因：① 接口可回退（项目有自建 SimpleOrchestrator 双实现）；② 确定性逻辑（分支/跳转/结束）必须按配置执行，不能交给 LLM；③ 状态可观测（执行到哪个节点要精确上报前端）。**节点之间必须确定，节点内部可以智能。**

### Q10：多智能体共享记忆怎么实现？
**A**：一次外呼 = 一个共享 `AgentState`（AgentScope 原生支持：构造函数 `Agent(state=...)` 注入，所有 handler 智能体共用同一状态）。效果：路由从「投诉处理」切到「还款安排」时，新节点直接看到完整对话历史（含其他节点说过的话），零重放成本。三个细节：① 意图分类 Agent 用独立状态——防止分类 JSON 污染对话上下文；② 打断时半句回复不落状态（回复在流正常结束才写入），已说句子由打断机制显式 observe 注入；③ 每个节点的 system prompt 前缀字节级稳定，缓存按节点命中。

### Q11：意图识别怎么做？
**A**：两级。**快路径**：意图配置里的关键词本地子串匹配（按意图声明顺序），0ms；**LLM 兜底**：AgentScope 结构化输出（pydantic schema `{"intent": 名称}`），分类 Agent 会话级缓存、独立状态、短输出；结果归一（不在意图列表 → 走兜底边）。还有**吸附模式**（sticky）：处理节点可配置「未命中关键词时留在本节点追问、不重新分类」——追问节奏优化，默认关。分类失败/异常全部降级走兜底，绝不炸通话。

### Q12：处理节点的话术 prompt 怎么组装？为什么？
**A**：**人设打底 + 节点话术追加**（非替代）。曾经实现成节点 prompt 完全替代人设，实测翻车：LLM 只看到一句孤立指令（「就耽误客户5秒」），没有身份背景，自己脑补成「企业 AI 服务商」开始推销。改为「人设 system prompt + ## 本环节话术要求（必须遵守）+ 节点话术」后问题消失，且前缀按节点字节级稳定，缓存友好。教训：给 LLM 的 system prompt 必须是**完整身份 + 增量约束**。

### Q13：结构化输出和工具调用是怎么用的？
**A**：结构化输出：`reply_stream(structured_schema=IntentResult, yield_final_msg=True)` → 取 final Msg 的 `structured_output`，意图 JSON 有类型保障。工具调用：工具包装成 `FunctionTool` 注册进 `Toolkit`，handler 创建时注入 `Agent(toolkit=...)` → ReAct 循环自动调用 → 结果进对话上下文。**一个实测坑**：AgentScope 2.0.12 以 `**kwargs` 扁平调用工具函数（传 params 实例会 TypeError）——所以插件的 `Params` 类只作 JSON schema，`run` 的形参必须与字段一一对应，加载器会校验并拒绝不符的插件。

### Q14：为什么流程图的节点不是 AgentScope 的 agent node？
**A**：因为流程骨架需要**确定性 + 可观测 + 可替换**：分支/跳转/结束语必须按配置走（客户说「投诉」必然走投诉分支，关键词匹配毫秒级本地完成）；当前执行节点要实时高亮到前端画布；编排层要能回退自建实现。AgentScope 智能体只在处理节点**内部**被调用（纯文字进出）。原则：「节点内部可智能，节点之间必须确定」。未来上多智能体协作（如催收谈判 Agent 组），只需新增一个编排层实现，流程图不动。

## 四、话术引擎与数据设计

### Q15：意图中枢状态机怎么设计？
**A**：`FlowRunner` 状态机四态（INIT/AWAITING/REPLYING/ENDED）：
- 会话开始 → 开场白节点（文本直读 / 人设开场白 / LLM 兜底三选）；
- 每轮客户转写 → 关键词快路径 →（未命中）LLM 分类 → 路由：意图边 → 对应 handler 流式回复 → 回 AWAITING 循环；兜底边 → 默认 handler；**连到 end 节点的意图边 = 结束语义** → 播结束语 → `end` 消息 → 前端播完自动挂断（bye 落库）；
- **打断契约**：外部取消回复生成器 = 打断，finally 保证状态回 AWAITING，新转写可立即投递；打断结束语 = 回到对话（客户后悔了还能继续）；
- IO 全部依赖注入（开场流/回复流/分类器/结束回调），纯逻辑可脱离 LLM 单测（13 个用例 fake 注入）。

### Q16：流程图定义与校验怎么做？
**A**：定义是 JSON（nodes + edges），draft 与 published 同构，编辑器与引擎共用一份 schema。校验规则（发布时执行，纯函数返回错误列表）：opening/intent 恰一个、handler/end 至少一个、节点/边 id 唯一、边端点存在、opening 无入边恰一出边、end 无出边、intent 出边带意图（兜底边至多一条、意图名唯一）、handler 出边必须回连 intent、opening 可达全图；另有工具绑定校验（绑定的工具必须属于本场景或为内置工具）。发布 = 校验通过 → 快照 + 版本 +1；**回滚 = 历史快照重新发布为新版本**（历史只增不改，全程留痕）。

### Q17：工具系统怎么设计？
**A**：三轨 + 统一注册：
- **HTTP 配置式**：工具库页面填 URL/方法/参数表 → 运行时 `pydantic.create_model` 动态生成参数 schema + 通用 HTTP 执行器（含 5s 超时）——**热生效，零代码**；
- **代码插件式**：按四要素约定写 Python 文件（TOOL_NAME/DESCRIPTION/Params/async run）放插件目录，启动 importlib 扫描加载、缺要素跳过不阻断启动；
- **内置基础工具**（如 kb_search）：scene_id 为空、所有场景默认可见、不可删除，种子幂等。
工具执行失败返回「工具调用失败：原因」文本（LLM 能看到并换策略），不向调用方抛异常。

### Q18：数据库怎么设计？为什么用 JSONB？
**A**：PostgreSQL 16 + SQLAlchemy 2.x。核心表：场景（资产组织单元）、人设（场景外键 + 激活互斥）、流程（一场景一流程，draft/published JSONB + 版本号）、流程版本快照、工具、客户、通话记录。流程图定义存 JSONB：**draft 与 published 同构、前端编辑器与后端引擎共用 schema**，不需要为每个节点类型建表；通话记录存转写气泡流 JSONB（[{role, text, ts}]），查询少、写入多，避免复杂关联。发布快照单独成表——回滚 = 快照重发布，历史只增不改。

### Q19：通话记录为什么会有「未接」状态？落库时机怎么设计？
**A**：外呼模式下 AI 先开口，客户可能全程不说话——按气泡流分类：无任何气泡不记录（模型未就绪即断开）；有 bot 气泡无 user 气泡 = no_answer（未接）；含 user 气泡 = connected（接通）。落库时机：前端主动断开（bye）→ 立即落库；意外断开（HMR/刷新）→ 60s 空闲兜底——否则开发期每次热更新都会冒出噪音记录（曾真实发生：42 秒的「您好你好」假记录）。教训：**开发工具的副作用要当成产品逻辑来设计**。

## 五、前端与全栈

### Q20：前端架构与关键页面
**A**：Vue 3 + TypeScript + Vite + Tailwind CSS v4（暗/亮双主题 CSS 变量，信号色板 teal=本地/打断、blue=云端、green=在线）。关键页面：对话工作台（实时转写气泡流 + 波形 + 打断计数 + 延迟统计）、流程图编辑器（vue-flow 画布：四类自定义节点、连线规则前端强制、属性面板、发布/回滚）、场景/工具/人设/客户/模板库管理页。实时链路 = 信令 WebSocket：offer/answer/ICE + PCM 二进制帧 + 文本事件（transcript/utterance/reply/audio/stop_audio/end/playback_done）。

### Q21：vue-flow 踩过什么坑？
**A**：TypeScript 递归泛型问题（TS2589：`Node`/`Edge` 类型的 label 字段为 `string | VNode | Component`，深度实例化爆炸）。解决：定义**浅类型** `VFNode/VFEdge`（只含业务需要的字段，结构化兼容组件 props），映射纯函数在浅类型与业务定义之间转换——顺带把「定义↔画布」双向映射做成可单测的纯函数。另一个小坑：`@vue-flow/background` 包没有独立 style.css（样式内联），多余导入会直接报错。

### Q22：前后端实时协议怎么设计？
**A**：信令 WebSocket 单通道多消息类型：控制类（offer/answer/ice/bye/playback_done）、上行音频（二进制 PCM 帧）、下行事件（status/transcript/utterance/reply/audio/stop_audio/end）。几个关键语义：① **playback_done**：前端确认播放到的帧序号，打断窗口据此收敛（后端发完 ≠ 前端播完）；② **end**：流程结束后端通知，前端等结束语播完自动断开（不截断音频）；③ 断线语义：bye = 主动断开立即落库，意外断开走空闲兜底（防 HMR 噪音）。所有消息 JSON 带 type 校验，非法消息直接拒绝。

## 六、工程实践

### Q23：测试策略？
**A**：后端 pytest 215 用例（全部依赖 docker PostgreSQL）：纯函数优先单测（分块/校验/状态机 fake 注入）、API 层用 TestClient 集成测试。前端 vitest 10 用例 + vue-tsc 类型检查。两个铁律（都是踩坑换来的）：① **测试数据防污染生产库**——测试只清理自己创建的数据（按 id/前缀精确删除），曾经测试假数据混进用户通话记录；② 测试不得改变用户状态——比如测试激活人设后要恢复**测试前**的激活态，而不是硬编码恢复默认。云端服务（ASR/TTS/LLM）不进自动化测试，靠真实 Key 联调 + 日志验收。

### Q24：工程规范有哪些？
**A**：Conventional Commits + 分支规范（新功能必须开分支，合并 main 走 fast-forward）；先思路后代码（方案批准才写码）；函数注册表（每个函数签名+职责登记，与代码同步更新）；ruff/vue-tsc 静态检查提交前必过；文档先行（PRD/WBS/踩坑复盘）；依赖 pin 死（torch==2.11.0 等——驱动/CUDA/库版本互锁，随意升级即翻车，全部有复盘文档）。

### Q25：如果一个功能上线后延迟突然变高，你怎么排查？
**A**：分层定位：① 看日志里每段的耗时锚点（VAD 端点→收尾启动→完整转写→回复首 token→首段合成→音频发出），先确定慢在 ASR、LLM 还是 TTS；② ASR 慢 → 看是否走了 LLM 意图分类（关键词快路径是否命中）、云端任务是否串行等待；③ LLM 慢 → 看 prompt 前缀是否变化导致缓存失效（人设/节点话术是否被改）、历史是否超预算；④ TTS 慢 → 看切段策略（标点切分）与合成并发；⑤ 全程网络延迟看 httpx 日志的请求耗时。这个项目把「可观测性」当硬标准，每个关键节点都有 INFO 日志。

### Q26：如何保证 LLM 应用的输出质量与安全？
**A**：三层：**约束层**（system prompt 内置合规红线：催收禁威胁恐吓、禁冒充公检法、禁索要验证码…每个行业模板自带）；**结构层**（能确定性的不交给 LLM：意图关键词、流程校验、结构化输出 JSON、发布前图校验）；**兜底层**（分类失败走兜底边、工具失败返回错误文本、LLM 异常不阻断通话）。金融场景的拒答/溯源（无据拒答转人工）在 WBS 中作为独立任务规划，属合规阶段。

### Q27：项目里延迟与成本的量化指标？
**A**：TTFT 目标 <500ms；意图关键词路径 0ms 附加、LLM 分类约 150~300ms（短输出 + 前缀缓存）；打断链路（VAD 起音判定 → stop_audio 发出）实测约 13ms；本地模型显存 RTX 4060 8GB 可承载（ASR+TTS 常驻，进程级单例共享）；上下文缓存命中让每轮 LLM 输入成本稳定（前缀不变只算增量）。
